## C12 알람 설계

- 메모 필드: `alarm_repeat: u8`(REPEATS 순번), `alarm_lead: u16`(분), `alarm_more: Vec<NaiveDateTime>`. 예전 저장 파일은 기본값(반복 없음)으로 읽힌다.
- `due_now`는 메모마다 알람 하나만 돌려준다: 본 알람 → 지난 추가 알람 → 미리 알림 순서.
- 반복 알람의 ‘확인’은 `next_repeat`로 지금 이후 첫 시각으로 넘긴다(며칠 놓쳤어도 한 번만 울림). 매월 31일은 짧은 달의 말일로 맞춘다.
- 반복 알람의 ‘5분 뒤’는 추가 알람을 하나 넣는다. 본 알람 시각(반복 기준)이 바뀌지 않게 하려는 것.
- 미리 알림을 확인하면 `(메모, 본 알람 시각)`을 기억해 다시 울리지 않는다. 이 기억은 저장하지 않아서, 미리 알림 구간에 프로그램을 다시 켜면 한 번 더 울릴 수 있다.
- Windows 알림 버튼 인자는 `done:14p`처럼 어느 알람인지 글자(m 본 알람, p 미리, x 추가)를 붙인다. 예전 형식(`done:14`)도 읽는다.

## C13 글자 색 설계

- `Format`에 `color`, `highlight`(팔레트 순번, 0은 없음)를 더했다.
- 저장은 기존 `spans` 튜플을 건드리지 않고 `TabRec.span_colors`를 나란히 둔다. 색을 하나도 안 쓴 탭은 비워 두어 저장 파일이 그대로다.
- 색을 칠할 때는 선택한 글자마다 지금 서식을 그대로 두고 색만 바꾼다(굵게 등이 풀리지 않음).
- 형광펜만 칠하고 글자 색이 기본이면, 어두운 테마에서도 읽히게 글자를 진한 색으로 그린다.
- 표 칸에는 아직 색이 저장되지 않는다(표 칸 서식은 예전 4가지 그대로).

## v2.0.1 이후: 검색 단축키, 빈 일정 메모

- 전역 단축키 Ctrl+Alt+F(검색)를 없앴다. 설정 › 단축키의 전역 단축키는 빠른 메모·캘린더 분리창·새 스티커 세 개만 남는다(`shortcuts: [String; 3]`; 예전 설정 파일의 네 번째 값은 읽지 않는다).
- 메인 창에서는 어느 화면이든 Ctrl+F를 누르면 왼쪽 검색창으로 커서가 간다(`main_shortcuts` → `search_shortcut`). 설정 화면은 닫히고, 사이드바가 접혀 있으면 열고, 아이콘만 보이는 좁은 폭이면 200으로 넓혀 검색창이 보이게 한다. 보던 화면은 그대로다.
- 전체메모의 ‘목록에서 찾기’는 더 이상 Ctrl+F를 쓰지 않는다(입력칸을 눌러 쓴다). 찾아 바꾸기는 Ctrl+H 그대로. 스티커 안의 Ctrl+F는 예전대로 전체메모 찾기로 간다.
- 캘린더에서 날짜를 끌어 만든 메모를 제목·본문·그림·표 없이 닫으면 영구 삭제한다(`drafts`, `drop_blank_drafts`, 휴지통을 거치지 않음). 무엇이든 쓴 메모, 다른 방법으로 만든 빈 메모는 그대로다.
- 테스트: `ctrl_f_in_the_main_window_puts_the_cursor_in_the_search_box`, `a_calendar_drag_memo_closed_blank_is_erased_and_a_written_one_stays`. GUIDE_VERSION 7.

## 설정에서 같은 메뉴로 돌아가기

- 증상: 내 작업실을 보다가 설정을 연 뒤 다시 ‘내 작업실’을 누르면 설정 화면이 그대로였다. 설정은 ‘보던 페이지가 바뀌면 닫는다’로만 닫혀서, 같은 페이지를 누르면 아무 일도 없었다.
- 수정: 메뉴(넓은 사이드바·아이콘 사이드바)의 페이지 버튼은 `open_page`로 페이지를 정하고 설정을 닫는다. 설정이 열려 있는 동안에는 뒤의 페이지 버튼을 선택 표시하지 않는다.
- 테스트 `choosing_the_page_behind_the_settings_leaves_the_settings`.
- 고침: 빈 일정 메모를 지운 뒤에도 캘린더·목록에 ‘삭제된 메모’ 줄이 남던 것. 목록은 입력이 있어야 다시 계산하는데, 지우기는 닫은 다음 프레임에 입력 없이 일어나서 예전 목록(제목만 ‘삭제된 메모’로 바뀐)이 그대로 보였다. 지울 때 `lists::CHANGES`를 올려 바로 다시 계산하게 했다.

## 일정 막대 양끝 끌어 기간 바꾸기, 본문 우클릭 삭제

- 캘린더 일정 막대의 실제 시작·끝 칸(주가 넘어가며 잘린 끝은 제외)에 7px 손잡이를 두었다(`band_edges`). 마우스를 올리면 ↔ 커서와 얇은 선이 보인다. 메인 캘린더와 캘린더 분리창이 같은 `calendar_bands`를 쓰므로 두 곳 모두 동작한다.
- 끄는 동안(`band_resize`, 창별)에는 반대쪽 끝을 고정하고 포인터 아래 날짜(`grid_day`)까지를 바로 메모 기간으로 바꾼다(`Note::set_days`). 포인터 이동은 입력으로 세지 않으므로 바꿀 때 `lists::CHANGES`를 올려 막대를 다시 그린다. 놓으면 "A ~ B 기간 일정으로 바꿨어요" / "A 당일 일정으로 바꿨어요" 안내.
- `set_days`: 이날까지 업무를 풀고(마감일과 막대가 어긋나지 않게), 시작일·일수를 정한다. 하루가 되면 당일 일정. 완료된 메모는 늘려도 모든 날이 완료로 남고, 하루로 줄이면 그날의 완료 여부를 따른다.
- 반복 일정과 ‘일정’ 기준이 아닌 캘린더(작성일·알람 기준)에서는 손잡이를 두지 않는다.
- 스티커 본문 우클릭 메뉴에 ‘스티커 휴지통으로’, ‘스티커 영구삭제…’를 더했다. … 더보기의 같은 동작(`trash_note`, 확인 창이 있는 `request_purge`)을 부른다.
- 테스트: `dragging_a_band_end_makes_a_stretch_and_back_a_single_day`, `stretching_a_deadline_memo_makes_it_a_plain_schedule`, `a_done_memo_stays_done_when_its_days_change`, `the_pointer_picks_the_grid_day_and_stays_inside_the_grid`. GUIDE_VERSION 8.

- 메뉴·팝업이 자기 창에 갇히던 문제: egui의 `context_menu`·`popup_below_widget`은 같은 창 안에만 그려져서, 작은 스티커나 캘린더 분리창·대화 상자에서는 잘렸다. 새 모듈 `src/float.rs`가 메뉴를 테두리 없는 항상 위 작은 창으로 띄운다(기존 스티커 ⋯ 메뉴의 `studio::menu_window` 재사용). 메뉴는 항목을 누르면 닫히고(글 입력칸·`keep_open` 행 제외), 팝업은 내용이 `close_popup()`을 부를 때 닫힌다. 둘 다 Esc, 원래 창을 누를 때, 포커스가 다른 곳으로 간 지 0.3초 뒤 닫힌다.
- 바꾼 곳: 스티커 본문 우클릭(편집·읽기 전용), 본문 탭 우클릭(‘숨긴 탭 보이기’ 하위 메뉴는 같은 메뉴 안에 펼침), 링크 이름 메뉴, 표 우클릭(‘표 삭제…’는 같은 메뉴에서 한 번 더 확인), 스티커 아래 툴바 팝업(글꼴·크기·색·투명도), 시간 고르기 팝업(알람·일정 창), 목록 행 우클릭(분리 캘린더의 날짜 목록 포함), 인라인 편집의 프로젝트·연결 메모 팝업, 캘린더 분리창 우클릭 보기 메뉴.
- 메인 창 안의 위키·전체메모·보드 메뉴는 창이 커서 그대로 두었다(하위 메뉴가 많아 같은 방식으로 옮기려면 따로 손봐야 함).
- 클립보드 히스토리: DB 스키마 2(`comment`, `pinned` 열, 1에서 자동 추가). 정렬은 압정 → 코멘트 있음 → 복사한 순(최신 먼저). 페이지 커서를 (순위, 시각, id)로 바꿔 순서가 페이지를 넘어도 같다. 검색이 코멘트도 찾는다. 압정 항목은 개수·기간·용량 자동 정리에서 빠진다(직접 하는 ‘이전 삭제’, ‘전체 삭제’는 그대로 지움). 행: 내용 · 코멘트(입력칸, 포커스를 잃을 때 저장) · 압정 · 복사 · 삭제. 다섯 필터 탭 모두 같은 목록을 쓴다.
- 편의기능: 표·이미지 모아보기에 압정(메모·탭·블록 id로 기억), 링크·즐겨찾기에 코멘트와 압정(주소로 기억). 링크는 압정 → 코멘트 → 가져온 순. 즐겨찾기 목록 자체도 이제 저장된다(전에는 실행 중에만 유지).
- 스탠딩 캘린더 ‘지원 안 됨’은 Windows 11 24H2(빌드 26100)에서만 보인다(`system::standing_unsupported_on`). 25H2(26200) 이후는 지원으로 본다.
- 테스트: float 열기·닫기, 24H2 판정, 클립보드 정렬·페이지·자동 정리·스키마 이전, 즐겨찾기 정렬, 압정·코멘트 저장 왕복. GUIDE_VERSION 10.

## 스탠딩 캘린더: 아이콘 아래로 되돌림, 해제 버튼, 끌어 놓기

- 증상(이 PC, Windows 11 25H2): 스탠딩 캘린더 위에 바탕화면 아이콘을 둘 수 없고, 해제 버튼이 듣지 않았다.
- 원인: 11-17 수정(fa3d943)이 새 바탕화면 구조(Progman 아래 `SHELLDLL_DefView`·`WorkerW`가 자식)에서 캘린더를 자식 창으로 붙이지 않고 바탕화면 바로 위의 최상위 창으로 두게 했다. 그러면 캘린더가 아이콘을 덮는다. 또 그 창은 클릭을 직접 받아서, 같은 클릭을 바탕화면 클릭 감시(마우스 훅)도 잡았다. 훅이 먼저 풀고 다음 프레임에 창의 클릭이 다시 고정해, 해제가 안 되는 것처럼 보였다.
- 수정(`win_style::desk::pin_under_icons`): 새 구조에서는 배경화면 앱들이 하는 방식으로 캘린더를 Progman의 자식으로 만들어 아이콘 층 바로 뒤, 배경(WorkerW) 앞에 둔다. Progman은 자기 그리기 표면이 없어 일반 자식 창은 안 보이므로, 불투명(255) 레이어드 창으로 만든다. 해제하면 레이어드를 뺀다. Explorer가 순서를 바꾸면 `keep_on_desktop`이 250ms마다 아이콘 층 바로 뒤로 되돌린다. Windows 11 24H2(26100)에서는 예전처럼 최상위 창 방식으로 둔다.
- 해제 직후 0.6초 동안은 스탠딩 버튼 클릭을 무시한다(`Dock::unpinned_at`). 그래서 같은 클릭이 두 경로로 들어와도 다시 고정하지 않는다.
- 스탠딩 중인 캘린더 위에 스티커를 끌어 놓아도 일정이 되지 않는다(`schedule_target_at`이 그 창의 날짜 칸을 건너뜀). 24H2 이외 버전도 마찬가지다.
- 확인(시험용 프로필, 이 PC 25H2): 고정하면 캘린더가 Progman 안에서 `SHELLDLL_DefView`와 `WorkerW` 사이에 놓였다. 화면에 보이고, 바탕화면 아이콘이 그 위에 그려졌다. Ctrl+Alt+C로 풀면 제목 표시줄이 있는 일반 창으로 돌아오고 레이어드 표시도 빠졌다.
- 확인 못 함: 바탕화면에서 스탠딩 버튼을 직접 눌러 푸는 것(바탕화면 클릭 권한을 받지 못함), 스티커를 실제로 끌어 놓는 것(단위 테스트만), 24H2 PC.
- 테스트 `nothing_dropped_on_a_standing_calendar_becomes_a_schedule`. GUIDE_VERSION 11.

## 바탕화면에서 스티커를 옮기면 일정 날짜가 바뀌던 문제

- 증상(사용자 확인, 25H2): 스탠딩 캘린더 위로는 일정이 들어가지 않지만, 이미 일정이 있는 메모의 스티커를 바탕화면에서 옮기면 캘린더 안에서 날짜가 바뀌었다.
- 원인: 스티커를 놓을 날짜는 최근 1초 안에 그려진 캘린더 칸 중에서 고른다. 최소화되었거나 다른 창·바탕화면 뒤에 가려진 메인 창 캘린더도 칸을 계속 그리고 있어 후보가 됐다. 창 순서 판정(`window_rank_at_origin`)은 최소화된 창을 찾지 못해도 후보에서 빼지 않았다.
- 수정(`system::window_seen_under_pointer`, `schedule_target_at`): 포인터 아래의 창을 위에서부터 훑어, 실제로 그 자리에 보이는 우리 캘린더 창만 날짜를 받는다. 끌고 있는 스티커·메뉴 같은 우리 창은 투과해서 보고, 다른 프로그램 창이나 바탕화면이 먼저 나오면 아무 날짜도 받지 않는다. 숨은 창, 최소화된 창, 가려진(cloaked) 창, 클릭 투과(WS_EX_TRANSPARENT) 창은 건너뛴다.
- 확인(시험용 프로필): 보이는 메인 캘린더 11/24 칸에 스티커를 놓으면 11/24로 바뀐다(그대로 동작). 메인 창을 최소화한 뒤 같은 자리(바탕화면)에 놓으면 스티커만 옮겨지고 날짜는 11/24 그대로였다.
- 단위 테스트에서는 실제 창이 없어 이 확인을 건너뛴다(`cfg(test)`).

## 스탠딩 중 바탕화면에서 마우스가 가끔 끊기던 문제

- 증상(사용자): 프로그램이 켜져 있을 때 바탕화면에서 마우스를 움직이면 가끔 프레임이 끊기고, 프로그램을 끄면 사라졌다.
- 원인으로 본 것: 스탠딩 중에는 캘린더 자리를 지키려고 0.25초마다 프로그램 전체를 다시 그렸다(`request_repaint_after(250ms)`). 아이콘 아래로 옮긴 뒤로는 그 캘린더가 바탕화면(Progman) 안의 레이어드 창이라, 다시 그릴 때마다 바탕화면 전체가 다시 합성된다. 스탠딩이 아닐 때는 주기적으로 깨는 곳이 없다(대기 최대 30초).
- 수정: 자리 지키기를 바탕화면 클릭 감시 스레드로 옮겼다. 이 스레드가 0.25초 타이머로 순서만 확인하고, 틀어졌을 때만 `SWP_ASYNCWINDOWPOS`로 바로잡는다. 그래서 감시 스레드가 UI 스레드를 기다리지 않고, 마우스 훅도 막히지 않는다. 프로그램은 스탠딩 때문에 다시 그리지 않는다. 풀린 창(도구 창 표시가 빠진 최상위 창)은 건드리지 않아서, 해제 직후의 타이머 한 번이 창을 내리지 않는다.
- 측정(시험용 프로필, 스탠딩 중 10초): 프로그램 CPU 172ms → 16ms.
- 확인: 고정하면 아이콘 아래에 보이고 메모 막대도 보인다. 창 순서를 일부러 배경 아래로 내리면 0.6초 안에 아이콘 바로 뒤로 돌아온다. Ctrl+Alt+C로 풀린다.
- 확인 못 함: 마우스 끊김이 사라졌는지는 사용자 화면에서 확인해야 한다.

## 스티커를 스탠딩 캘린더 위에 두고 마우스를 흔들면 잠시 뒤 끊기던 문제

- 증상(사용자): 스탠딩 캘린더 위에 스티커를 두고 마우스를 흔들면, 잠시 뒤 한 번씩 짧게 끊겼다.
- 원인: eframe은 창 하나를 다시 그릴 때 모든 창(immediate viewport)을 함께 그린다. 같은 그림이면 건너뛰는 패치(`vendor/eframe`, 36b6592)가 있지만, 안전을 위해 3초 넘게 안 그린 창은 다시 그린다(`REPAINT_AFTER`). 마우스를 계속 움직이면 프로그램이 계속 깨어 있으므로, 아이콘 아래의 큰 캘린더가 3초마다 한 번씩 다시 그려졌다. 그때 바탕화면 전체가 다시 합성되며 끊겼다.
- 수정: 앱이 창별로 `eframe_keep_frame`(주기적 다시 그리기 없이 마지막 그림 유지)와 `eframe_paint_once`(이번에 한 번 그리기)를 eframe에 알릴 수 있게 했다. 스탠딩으로 고정된 캘린더는 그림이 실제로 바뀔 때만 그린다. 고정·해제 직후에는 한 번 그린다(고정 직후 다시 그리기도 요청).
- 창 순서 확인은 1초마다로 늦췄다. 다시 그리지 않고 창 순서만 조회하므로 끊김과는 무관하다. 순서는 배경화면 바꾸기, Explorer 재배치처럼 드문 경우에만 바뀐다.
- 확인(시험용 프로필, 그리기 기록을 임시로 남겨 확인한 뒤 뺐다): 고정 후 스티커 위에서 6초 동안 마우스를 흔드는 동안 캘린더는 한 번도 다시 그려지지 않았다. 고정 직후 캘린더가 보였다. 스티커 제목을 'test 22'로 바꾸자 캘린더 막대도 바로 바뀌었다.
- 확인 못 함: 사용자 화면에서 끊김이 사라졌는지.

## 스티커만 띄워도 마우스를 움직이면 끊기던 문제 (3초마다 모든 창 다시 그리기 제거)

- 증상(사용자): 새 스티커 하나만 바탕화면에 띄우고 마우스를 움직여도 한 번씩 끊겼다.
- 측정(시험용 프로필, 임시 그리기 기록): 마우스가 우리 창 위에서 움직여 프로그램이 깨어 있는 동안, 3초마다 모든 창(메인·스티커들·보이지 않는 보조 창)이 한꺼번에 다시 그려지고 화면 전환(swap)됐다. vendor eframe의 '같은 그림은 건너뛰기'에 들어 있던 안전장치 `REPAINT_AFTER`(3초) 때문이다. 이 PC는 swap 한 번에 10~15ms가 들어(성능 기록 11-18), 창 네 개면 한 번에 수십 ms 동안 멈춘다.
- 수정(`vendor/eframe/src/native/glow_integration.rs`): 시간이 지났다는 이유만으로는 다시 그리지 않는다. 대신 창의 최소화·최대화·포커스 상태가 바뀐 프레임에는 그림이 같아도 그린다. 그 안전장치가 노리던 '다시 보일 때 그림이 사라진 창'은 이런 순간에만 생긴다. 앞 단계의 `eframe_keep_frame`은 필요 없어져 지웠다(`eframe_paint_once`는 스탠딩 고정·해제 때 그대로 씀).
- 메인 창이 최소화되어 있으면 페이지를 그리지 않는다(빈 판만). 스티커 위에서 마우스가 움직일 때마다 메인 창의 페이지 배치까지 다시 계산하던 것(프레임당 약 0.3ms)이 빠진다. 되살리면 그 프레임에 바로 다시 그린다.
- 확인: 고친 뒤 스티커 위와 바탕화면에서 마우스를 흔드는 동안 3초마다 한꺼번에 그리기가 없었다. 그리기는 마우스 아래 스티커의 모양이 바뀔 때만 있었다. 메인 창을 최소화했다가 되살리면 마우스를 움직이지 않아도 바로 제대로 보였다. 스탠딩 고정 뒤 캘린더와 그 위의 스티커가 정상으로 보였다.
- 참고: 프레임 하나의 우리 코드 시간은 약 1.2ms(스티커 0.85, 메인 0.35)로 무겁지 않다. 마우스를 움직이면 이동 한 번에 프레임이 2~3번 돈다(vsync 꺼짐). 아직 줄이지 않았다.
- 확인 못 함: 사용자 화면에서 끊김이 사라졌는지.

## 마우스를 한 번 움직이면 프레임이 2~3번 돌던 것 줄이기

- 측정(시험용 프로필, 스티커 위에서 6초 동안 커서를 약 350번 옮김, 임시 프레임 기록): 프레임 1032번, CPU 2.25초. 이동 한 번에 프레임이 약 3번 돈다. egui는 입력이 있으면 한 번 더 그리고, 창마다 자기를 다시 그려 달라고 따로 요청한다. 즉시 모드 창은 모두 부모(호스트) 프레임에서 함께 돌아서 요청마다 전체 프레임이 된다.
- 수정 1(`vendor/eframe/src/native/run.rs`): 같은 창의 프레임 사이를 최소 16ms(초당 약 60번)로 띄운다(`MIN_FRAME`, `spaced`). 그 사이에 온 요청은 한 프레임으로 합쳐진다. 창 크기 조절 중의 즉시 그리기(`RepaintNow`)는 그대로다.
- 수정 2(`vendor/eframe/src/native/glow_integration.rs`): 원시 마우스 이동(`DeviceEvent::MouseMotion`)으로는 프로그램을 깨우지 않는다. 우리 창에 포커스가 있으면 마우스가 화면 어디서 움직이든 마우스의 보고 속도대로 이 신호가 오는데, 이 프로그램은 쓰지 않는다. 우리 창 위의 이동은 `CursorMoved`로 깨운다.
- 결과: 같은 시험에서 프레임 1032 → 366(이동 한 번에 약 1번), CPU 2.25초 → 1.13초. 실제 마우스는 초당 수백 번 움직임을 보고하므로 차이가 더 크다(초당 60프레임에서 멈춤).
- 확인: 스티커에 빠르게 한글·숫자 입력이 빠짐없이 들어갔고, 스티커 끌어 옮기기가 정상이었다.
- 확인 못 함: 수정 2의 효과. 이 PC에서 합성 입력(SendInput)으로는 원시 이동 신호를 만들 수 없어, 고치기 전 빌드에서도 재현되지 않았다. 사용자 화면에서의 체감도 확인해야 한다.

## 툴바 위를 마우스로 지나갈 때 아이콘마다 끊기던 문제 (다시 그리기 전수 조사)

- 증상(사용자): 스티커 하단·상단 툴바 위로 마우스를 왕복하면 다른 아이콘 위를 지날 때마다 프레임이 떨어졌다.
- 측정 방법: vendor eframe에 창별 그리기·건너뛰기, 프레임 시간, 다시 그리기 요청, 직전 프레임과 달라진 그림 조각(clip rect·영역)을 남기는 임시 기록을 넣고, 시험용 프로필에서 커서를 툴바 위로 6px씩 왕복시켰다(4~6초). 기록은 확인 뒤 모두 뺐다.
- 원인 1 (가장 큼): 툴팁. egui는 툴팁 하나가 보인 뒤 0.2초(grace time) 안에 다른 위젯에 올라가면 기다리지 않고 바로 툴팁을 띄운다. 툴바를 쓸고 지나가면 아이콘마다 툴팁이 떴다 사라지기를 반복해, 6초 동안 프레임 365번 중 311번이 실제로 다시 그려졌다(바뀐 조각은 거의 툴팁). CPU 2.9초.
  - 수정(`src/ui.rs`): `tooltip_grace_time = 0`. 툴팁은 마우스가 한 위젯 위에 0.5초 머물 때만 뜬다. `show_tooltips_only_when_still`은 끄고 같은 조건을 지연 시간으로만 판단하게 했다.
  - 결과: 4초 쓸기에서 실제 그리기 311(6초) → 상단 44 · 하단 19. 이제 아이콘 경계를 넘어 강조색이 바뀔 때만 그린다.
- 원인 2: 다시 그리지 않는 프레임도 모든 창(메인·스티커 전부)의 화면 구성을 다시 계산한다(즉시 모드 창은 모두 호스트 프레임에서 함께 돈다). 프레임당 약 4~5ms. 마우스를 움직이면 egui는 포인터 속도가 0이 될 때까지 계속 프레임을 요청하므로 초당 60번 돌았다.
  - 수정(`vendor/eframe/src/native/run.rs`): 버튼을 누르지 않고 마우스만 지나가는 동안에는 창의 프레임 간격을 33ms(초당 약 30번)로 늘린다(`HOVER_FRAME`, `note_input`). 버튼을 누르거나(끌기·선택), 키 입력·휠·창 이동/크기 조절이 오면 다시 16ms다.
  - 결과: 4초 쓸기에서 프레임 245 → 121, CPU 약 1.7초 → 0.9초.
- 함께 조사한 것(문제 없음): 앱 코드의 `request_repaint` 24곳. 모두 끌기·창 크기 조절·토스트·표 높이 확정·종료 같은 조건이 있을 때만 요청한다. 마우스를 멈추면 프레임이 멈췄다(3초 동안 기록 없음).
- 테스트: `sweeping_over_a_toolbar_pops_no_tooltips_until_the_pointer_rests`(쉬면 툴팁이 뜨고, 옆 아이콘으로 지나가는 동안은 뜨지 않으며, 다시 쉬면 뜬다. egui 기본 grace time으로 되돌리면 실패하는 것을 확인함).
- 확인(시험용 프로필): 쉬면 툴팁이 뜬다. 스티커 입력(붙여넣기 방식), 머리 막대 끌어 옮기기 정상.
- 확인 못 함: 사용자 화면의 체감. 실제 마우스는 초당 수백 번 이동을 보고해 시험(SetCursorPos)과 다르다. hover 중 30fps가 눈에 띄게 느린지도 사용자 확인이 필요하다.

## 전역 최적화 1: 외장 GPU 대신 내장 GPU로 그리기

- 요청(사용자): 프로그램 전역 최적화(CPU·메모리·작동 속도·불필요한 연산·정보 중복 복제, 우클릭 메뉴, 설정창 배치, 툴바 간소화, 방어 조건).
- 발견: 이 PC는 화면을 Intel Arc(내장)가 출력하고 RTX 4070 Laptop(외장)이 따로 있는 하이브리드다. 프로그램이 NVIDIA OpenGL 드라이버(nvoglv64.dll)로 창을 그리고 있었다. 그러면 창마다 외장 GPU에서 그린 뒤 내장 GPU 화면으로 복사하고, 드라이버가 창(GL 컨텍스트)마다 스레드 약 16개·메모리 약 50MB를 잡는다.
- 측정(실제 데이터, 스티커 17개 + 메인): 작업 집합 451MB, 전용 메모리 916MB, 스레드 298개.
- 수정(`src/system.rs` `prefer_integrated_gpu`, `src/main.rs`): GL을 만들기 전에 프로세스 안에서만 `SHIM_MCCOMPAT=0x800000000`을 설정해 Windows가 절전(내장) GPU의 OpenGL 드라이버를 고르게 한다. 사용자가 이미 이 값을 정해 두었으면 건드리지 않는다. 창을 만든 뒤(`App::new`)에는 지워서(`forget_gpu_choice`) 이 프로그램이 여는 다른 프로그램(링크·파일 열기)에는 넘어가지 않는다. (아래 '전역 최적화 2'에서 고침: 이 방식은 실제로는 동작하지 않았다.)
- 결과(같은 실제 데이터): 작업 집합 249MB, 전용 메모리 73MB, 스레드 17개. 시험용 프로필 툴바 쓸기 4초 CPU 344ms → 219ms. 로드된 드라이버가 igxelpgicd64.dll(Intel)로 바뀐 것을 확인했다.
- 테스트: `the_gpu_choice_is_made_once_and_not_passed_on`(값이 없을 때만 정하고, 지우면 사용자가 정한 값은 그대로 둔다).
- 확인(시험용·실제 데이터): 스티커·메인 창·메뉴가 정상으로 그려졌다.
- 확인 못 함: 외장 GPU만 있거나 내장 GPU만 있는 PC. 이 값은 하이브리드가 아니면 무시된다(Windows 동작). 다른 하이브리드 구성(AMD 내장 등)은 시험하지 못했다.

## 전역 최적화 2: 내장 GPU 선택 바로잡기, 창 아이콘을 매 프레임 다시 풀던 문제

- 내장 GPU 선택 바로잡기:
  - 발견: 위 커밋 뒤 다시 재 보니 NVIDIA 드라이버(nvoglv64.dll)가 그대로 쓰이고 있었다(실제 데이터: 전용 메모리 1036MB, 스레드 323개).
  - 원인 1: 시험에 쓰던 터미널(Claude 앱에서 연 PowerShell)에 `SHIM_MCCOMPAT=0x810000001`이 이미 들어 있었다. NVIDIA GPU에서 도는 프로그램이 자기가 띄우는 프로그램에 넘기는 값으로 보인다. 코드는 이것을 '사용자가 정한 값'으로 보고 손대지 않았다. 앞 기록의 '수정 후' 측정은 이 값을 지우고 띄운 경우였다.
  - 원인 2: 값을 `App::new`에서 바로 지웠다. 드라이버는 창의 그리기 컨텍스트를 만들 때 이 값을 읽고, 스티커 창들은 첫 프레임에 만들어진다.
  - 수정: 사람이 손으로 정하는 두 값(`0x800000000` 내장, `0x800000001` NVIDIA)만 그대로 둔다. 물려받은 다른 값은 내장으로 바꾼다. 첫 프레임이 끝난 뒤(`update` 끝)에 원래 값으로 되돌린다: 없던 값은 지우고, 물려받은 값은 다시 넣는다. 링크를 열어 시작되는 프로그램은 원래 받을 값을 받는다.
  - 시험 중 확인한 것:
    - 프로세스 안에서 값을 바꿔도 효과가 있다. 드라이버가 시작 때가 아니라 GL을 만들 때 읽는다.
    - 프로세스를 다시 띄워(값을 넣어) 시작하는 방식도 시험했다. 새 프로세스가 시작하자마자 값을 지우면 NVIDIA로 돌아가서 버렸다.
- 창 아이콘(`src/app_icon.rs`):
  - 원인: 메인·스티커 창은 매 프레임 창 설정(`ViewportBuilder`)을 새로 만들면서 `app_icon::window()`로 128px ICO를 매번 다시 풀었다. eframe은 프레임마다, 창마다 모든 창의 설정을 비교한다. 즉시 모드 창 하나를 그릴 때마다 전체 창 목록을 처리한다. 그래서 아이콘 64KB 비교가 '창 수 × 창 수'번 일어났다.
  - 측정(임시 기록, 실제 데이터 18창): 스티커 위로 마우스를 움직일 때 호스트 프레임 한 번이 평균 17.5ms. 그중 창마다 화면 구성 뒤 처리(`handle_viewport_output`)가 약 0.17ms × 18이었다. 앱 자체의 스티커 그리기는 약 0.1ms였다.
  - 수정: 아이콘을 한 번만 풀어 `Arc`로 나눠 쓴다. 같은 `Arc`이면 비교가 포인터 비교로 끝난다.
  - 결과: 프레임당 17.5ms → 2.9ms. 창마다 뒤 처리 0.17ms → 0.007ms.
- 결과(실제 데이터, 스티커 17개 + 메인, 최종 빌드, 같은 터미널에서 실행):
  - 드라이버: igxelpgicd64.dll.
  - 메모리·스레드: 작업 집합 246MB, 전용 메모리 67MB, 스레드 17개.
  - 스티커 하단 위 4초 왕복의 CPU: 313~469ms. 고치기 전 NVIDIA + 아이콘 매 프레임일 때는 임시 기록을 켠 채 2188ms였다.
- 확인(시험용 프로필): 물려받은 값이 있는 채로 띄워도 Intel 드라이버를 썼고, 값을 되돌린 뒤 새 스티커(Ctrl+Alt+S)를 만들어도 NVIDIA 드라이버가 올라오지 않았다(스레드 17개 유지).
- 테스트: `the_integrated_gpu_is_asked_for_unless_chosen_by_hand_and_then_put_back`, `window_icon_decodes_to_a_square_rgba_buffer_near_128px`(같은 `Arc`를 돌려주는지 추가).
- 확인 못 함: 탐색기·시작 프로그램으로 띄운 경우(이 터미널 밖). 그 경우엔 물려받은 값이 없으니 '없던 값' 경로이고, 시험용 프로필에서 그 경로도 Intel인 것을 앞 기록에서 확인했다. 다른 PC 구성(AMD 내장 등)도 확인 못 함.

## 전역 최적화 3: 내장 GPU 선택 되돌림, 우클릭 메뉴, 하단 메시지, 설정 배치

- 내장 GPU 선택 되돌림 (위 '전역 최적화 1·2'의 GPU 부분 취소):
  - 발견: Intel 드라이버로 그리게 된 빌드를 시험용 프로필에서 화면으로 확인하니, 어떤 창에도 내용이 그려지지 않았다. 스티커는 빈 흰 상자였고, 메인 창은 검은 바탕에 흰 사각형만 있었다. 마우스를 올려도 그대로였다.
  - 같은 빌드를 `SHIM_MCCOMPAT=0x800000001`(NVIDIA)로 띄우면 정상으로 그려졌다.
  - 앞의 '67~73MB, 스레드 17개'는 그리기가 실패한 상태의 수치였다. '렌더링 정상'이라고 적은 앞 기록은 잘못이다.
  - 조치: `prefer_integrated_gpu`·`forget_gpu_choice`와 그 테스트를 지우고, `src/system.rs`를 v2.0.2 상태로 되돌렸다. 메모리·스레드는 v2.0.2와 같다(실제 데이터, NVIDIA: 전용 메모리 약 1GB, 스레드 약 320개).
  - 원인은 더 조사하지 않았다. eframe glow가 GL 컨텍스트 하나를 여러 창 표면에 번갈아 붙이는데, Intel 드라이버에서 이것이 실패하는 것으로 짐작한다. 이 PC 같은 하이브리드에서 메모리를 줄이려면 창별 컨텍스트, 또는 wgpu(D3D12) 백엔드 전환을 따로 검토해야 한다.
- 남은 성능 개선(유지): 창 아이콘을 한 번만 푸는 수정. NVIDIA 그대로 실제 데이터 18창에서 스티커 하단 4초 왕복의 CPU가 437~484ms였다(임시 기록을 켠 수정 전 측정은 2188ms. 기록 자체의 비용이 섞여 있어 정확한 비교는 아니다).
- 매 프레임 복사 줄이기:
  - `consume_body_project`: 열린 메모마다 매 프레임 본문 전체를 복사한 뒤 `#`로 시작하는지 봤다. 이제 먼저 보고, 맞을 때만 복사한다.
  - 편집기 끝의 `legacy_body` 갱신: 매 프레임 복사하던 것을 달라졌을 때만 `clone_from`으로 복사한다.
- 우클릭 메뉴(`src/composer.rs`):
  - 본문 메뉴: 잘라내기·복사·붙여넣기에 Ctrl+X/C/V를 표시했다. ‘모두 선택’(Ctrl+A)을 더했다. ‘원본 배율 100%’는 이미 100%이면 흐리게 한다.
  - 표 메뉴: 본문 메뉴와 같은 순서(잘라내기·복사·붙여넣기)로 맞추고 단축키(선택 영역 내용 삭제는 Delete)를 표시했다.
  - 링크 메뉴: ‘링크 열기’를 더했다.
  - ‘모두 선택’을 처음 만들 때, 선택 요청만 보내면 편집기가 첫 탭으로 돌아가는 것을 발견했다. 지금 탭을 함께 지정한다(`Document::select_all`).
- 하단 메시지(`expire_status`):
  - 증상: ‘되돌릴 내용이 없습니다’, ‘링크 주소를 복사했습니다’ 같은 메시지가 다른 메시지로 바뀔 때까지 스티커 아래에 계속 남아 한 줄을 차지했다.
  - 수정: 5초 뒤 저절로 사라진다. 새 메시지는 새로 5초를 센다.
  - 이미지 툴바의 ‘복사’는 성공·실패를 이 줄에 알린다. ‘삭제’에는 ‘Ctrl+Z로 되돌릴 수 있습니다’ 툴팁을 달았다(본문 되돌리기 기록에 들어감).
- 설정 배치(`src/desktop.rs`):
  - 일반: 자동 실행, 첫 화면, 메뉴 숨기기, 휴지통 보관 기간, 자동 잠금만 남겼다.
  - 메모창: ‘새 메모’, ‘스티커 동작’, ‘접기’, ‘본문 기본값’ 네 묶음으로 나눴다.
    - ‘스티커 동작’에는 일반에 있던 작업표시줄 표시, 체크완료 시 닫기·재정렬, 정렬 모니터, 매일 오늘 메모와 툴바 자동 숨기기를 모았다.
  - 캘린더: 일반에 있던 ‘메모 끌어 놓기 시 이날까지 업무 선택창 띄우기’를 옮겼다(캘린더에서만 쓰이는 기능).
  - 가이드의 위치 안내 두 곳을 고쳤다(GUIDE_VERSION 15).
- 스티커 도움말의 ‘상자를 두 번 클릭하면 복원’을 ‘상자를 누르면 복원’으로 고쳤다. 실제로는 한 번 누르면 펼쳐진다.
- 테스트:
  - `select_all_from_the_menu_stays_on_the_tab_shown`
  - `a_footer_message_goes_away_by_itself`
  - `each_settings_option_sits_with_what_it_changes`
  - 기존 설정 배치 테스트의 기준 항목을 바뀐 위치에 맞췄다.
- 확인(시험용 프로필, NVIDIA로 되돌린 빌드):
  - 창이 모두 정상으로 그려졌다.
  - 설정 › 일반·메모창의 새 배치를 확인했다.
  - 스티커 본문 우클릭 메뉴에 단축키 표시와 ‘모두 선택’이 보였고, ‘원본 배율 100%’는 흐렸다. ‘모두 선택’을 누르자 본문이 선택됐다.
  - Ctrl+Z로 ‘되돌릴 내용이 없습니다’가 떴다가 5초 뒤 사라지며 줄도 없어졌다.
- 확인 못 함: 표 메뉴와 링크 메뉴는 화면에서 열어 보지 않았다(코드와 빌드만).

## 툴바 간소화 보류, 방어 조건 점검

- 툴바: 표·이미지·스티커 툴바 간소화 안을 제안했다. 사용자가 '지금은 그대로'를 골라 바꾸지 않았다. 안은 인수인계 문서에 남겼다.
- 방어 조건 점검(코드 확인, 변경 없음):
  - 메모 인덱스: 메모는 목록에서 지워지지 않고, 영구삭제해도 `purged`·`deleted` 표시만 남는다. 열린 창·메뉴가 가진 인덱스는 다른 메모를 가리키지 않는다.
  - 시간 입력(`ui::time_input`): 시는 0~23, 분은 0~55(5분 단위)이거나 `step_minutes`로 범위 안에서만 바뀐다. 일정·알람의 `and_hms_opt(..).unwrap()`은 실패하지 않는다.
  - 끌기·창 이동의 `take().unwrap()` 네 곳은 모두 바로 앞에서 값이 있는지 확인한다.

## 전역 최적화 4: 손대지 않은 스티커 쉬기

- 문제: 모든 창이 한 프레임을 함께 돈다. 메인 창이나 스티커 하나 위에서 마우스만 움직여도, 열린 스티커가 모두 매 프레임 UI를 다시 만들고 테셀레이션했다.
- 방식:
  - `studio::may_rest`: 스티커는 아래 조건을 모두 만족하면 그 프레임에 UI를 만들지 않고 콜백에서 바로 돌아간다.
    - 자기 입력·포커스·메뉴·대화상자·끌기·창 명령이 없다(`Quiet::busy`).
    - 포인터가 창 바깥 160pt(`REST_NEAR`) 밖에 있다.
    - 마지막으로 다 그린 뒤 입력으로 데이터가 바뀌지 않았다(`lists::CHANGES`).
    - 마지막으로 다 그린 지 0.25초(`REST_MAX`)가 안 됐다.
  - 쉰 프레임에서 앱은 `eframe_rest` 임시 값을 남긴다. vendor eframe(`render_immediate_viewport`)은 그 창의 테셀레이션·그리기·스왑을 건너뛰고, 텍스처 변경과 창 명령만 처리한다. 창은 마지막 그림을 그대로 보여 준다.
  - 쉰 창이 있으면 메인 패스가 0.3초 뒤 다시 그리기를 요청한다. 포인터가 멈춘 뒤 모든 창이 한 번 더 다 그려진다.
  - egui 포커스가 남은 창은 쉬지 않는다. 쉰 패스에서 egui가 포커스를 놓아 커서가 사라지기 때문이다. 그래서 입력하던 스티커는 다른 창을 써도 계속 그린다.
  - 떠 있는 영역(이미지 툴바)이 보이던 창도 쉬지 않는다. 한 프레임이라도 빠지면 페이드인을 다시 한다. egui가 매 패스 등록하는 배경 레이어는 빼고 센다(`floating_area_shown`). 처음 넣었을 때 이 배경 레이어 때문에 모든 창이 쉬지 못한 것을 진단 기록으로 찾았다.
- 측정(실제 데이터, 스티커 17개 + 최대화한 메인 창, NVIDIA): 메인 창 아래쪽에서 4초 동안 왕복한 프로세스 CPU 시간이다.
  - 같은 조건에서 번갈아 측정했다. 기준(HEAD)은 266~469ms로 평균 약 373ms였다. 쉬기 적용은 141~359ms로 평균 약 242ms였다(약 35% 감소).
  - 최종 빌드 한 번 더: 219·250·313·234ms.
  - 측정 단위가 15.6ms이고 흔들림이 커서 대략적인 값이다.
- 진단 기록: 스티커는 약 8프레임에 1번만 다 그렸다. 포인터가 멈추고 0.3초 뒤 모든 창이 다시 다 그렸다.
- 확인:
  - 실제 데이터에서 스윕(메인 창 아래쪽) 직후 스티커가 빈 화면이나 깨진 화면 없이 그대로 보였다.
  - 쉬던 스티커의 버튼 클릭(시험용 프로필): 스티커 하나 위에서 1초 움직여 다른 스티커(warm1)를 쉬게 했다. 그 직후 SendInput으로 warm1의 탭 추가(+)로 옮겨 40ms 뒤 눌렀더니 탭이 추가됐다.
- 첫 클릭에 대한 검토:
  - egui는 직전 패스의 위젯 위치로 누름 대상을 찾는다. 쉰 패스 바로 다음 패스에 포인터 진입과 누름이 함께 들어오면 대상을 못 찾을 수 있다.
  - 실제 사용에서는 포인터가 창 160pt 안에 들어오면 매 프레임 다 그리므로, 창에 닿기 전에 위젯이 준비된다.
  - 간격 0(이동 직후 바로 누름)으로 같은 시험을 하면 쉬기 빌드는 클릭을 놓쳤다. 같은 조건에서 기준 빌드도 놓쳤다(비활성 창의 첫 클릭). 따라서 쉬기 때문에 새로 생긴 실패는 아니다.
  - 이 경우를 위해 이벤트 없이 한 번 더 도는 준비 패스를 vendor에 넣어 봤다. 효과를 확인할 수 없어 되돌렸다.
  - 바로잡음: 처음 한 클릭 시험은 이 Claude 앱 창이 화면 오른쪽(x≥1788px)을 덮고 있어서 무효였다. 그 창은 스크린샷에는 가려져 보이지 않았다. 움직임과 일부 클릭이 그 창으로 가서, 스티커가 실제로 쉬지 않은 상태로 시험했다. 위의 결과는 스티커를 덮이지 않는 곳에 두고 다시 한 것이다.
- 테스트: `a_window_rests_only_when_nothing_concerns_it`, `only_a_floating_area_keeps_a_window_built`.
- 확인 못 함:
  - 메인 창에서 바꾼 데이터가 쉬던 스티커에 바로 반영되는지 따로 보지는 않았다. 입력이 있으면 `CHANGES`가 올라 다음 프레임에 다 그리고, 아니어도 0.3초 안에 다시 그린다(코드로 확인).
  - 다중 모니터(배율이 다른 모니터)에서의 160pt 판정은 시험하지 않았다.

## 우클릭 메뉴 화면 확인, 본문 속 링크 메뉴

- 화면 확인(시험용 프로필): 스티커 본문 메뉴, 표 칸 메뉴(잘라내기·복사·붙여넣기·선택 영역 내용 삭제 순서와 단축키 표시)가 정상으로 열렸다.
  - 처음에는 표 메뉴가 열리지 않는 것처럼 보였다. 진단 기록으로 원인을 찾았다. 그 자리를 이 Claude 앱 창이 덮고 있어 클릭이 스티커에 닿지 않았다. 앱 문제는 아니었다.
- 개선: 본문 속 주소(http·https)를 우클릭하면 본문 메뉴 맨 위에 '링크 열기'와 '링크 주소 복사'가 나온다.
  - 전에는 본문 속 주소에서 일반 본문 메뉴만 열렸다. 링크 메뉴는 본문 아래 링크 목록에만 있었다.
  - 우클릭한 위치의 글자로 주소를 찾는다(`url_at`). 주소의 마지막 글자 오른쪽 절반을 눌러도 찾는다. 판정 규칙은 기존 `urls`와 같다.
  - 화면 확인: 주소 위에서는 두 항목이 나왔고, 일반 글자 위에서는 나오지 않았다. 사용자 클립보드를 덮지 않으려고 항목을 눌러 보지는 않았다.
- 테스트: `a_right_click_finds_the_web_address_under_it`, `a_right_click_on_a_table_cell_opens_the_table_menu`.

## 전역 최적화 5: 스티커 안에서 움직일 때 메인 창 쉬기

- 문제: 메인 창이 열려 있으면, 그 앞의 스티커 위에서 마우스만 움직여도 메인 창이 매 프레임 UI를 다시 만들었다(약 1ms).
- 방식: 스티커 쉬기와 같은 `studio::may_rest`를 메인 창에도 쓴다(`Studio::main_quiet`).
  - 바쁨 판정은 스티커와 메인 창이 함께 쓰도록 `window_busy`로 묶었다. 입력·포커스·메뉴·떠 있는 영역·끌기·선택 상자 등이 있으면 쉬지 않는다.
  - 포인터 조건은 다르다. 메인 창은 포인터가 열린 스티커 안쪽으로 24pt(`MAIN_REST_INSET`) 이상 들어가 있을 때만 쉰다. 그 위치에서는 스티커가 앞에 있으므로 메인 창이 포인터를 받지 않는다. 스티커 가장자리를 벗어나기 전에 메인 창이 다시 다 그려진다.
  - 포인터 위치는 OS 커서 좌표(`system::cursor_pos`)와 각 스티커 창의 바깥 사각형(물리 픽셀)으로 비교한다.
  - 데이터가 바뀌면(`lists::CHANGES`) 바로 다 그리고, 아니어도 0.25초마다 한 번은 다 그린다.
- 측정(실제 데이터, 4초 왕복, 최종 빌드와 번갈아 2회씩 3번, 프로세스 CPU 시간):
  - 스티커 위: 기존 359·375·391·297·672·750ms(평균 약 474ms), 적용 219·203·391·219·219·391ms(평균 약 274ms).
  - 메인 창 아래쪽: 기존 평균 약 362ms, 적용 평균 약 297ms. 이 경우는 메인 창이 쉬지 않으므로 흔들림 범위의 차이로 본다.
  - 측정 단위가 15.6ms이고 흔들림이 커서 대략적인 값이다.
- 확인(시험용 프로필):
  - 스티커(test 22) 안에서 마우스를 움직이며 글자를 입력했더니, 메인 창 목록 제목이 바로 'test 22x'로 바뀌었다(데이터 변경 시 바로 다 그림).
  - 스티커 안에서 움직인 직후 메인 창 사이드바 '캘린더'를 누르자 바로 캘린더로 바뀌었다.
- 테스트: `input_keeps_a_window_built`(입력이 있는 패스에서는 창이 바쁨).
- 확인 못 함: 스티커가 메인 창 밖으로 걸쳐 있거나, 배율이 다른 모니터에 있을 때의 판정은 따로 시험하지 않았다. 판정이 틀려도 결과는 메인 창이 쉬지 않는 쪽(기존과 같음)이다.
