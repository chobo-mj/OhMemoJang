# 성능 최적화 1차 (창 크기 조절·유휴 상태)

## 방법
추측하지 않고 측정부터 했다. 임시 계측(프레임 구간 시간, 메인 스레드 샘플링)과 메인 창을 SetWindowPos로
계속 흔드는 스크립트로, 같은 조건(내 PC, 실제 메모)에서 전/후를 비교했다. 계측 코드는 모두 제거했다.

## 찾은 것
1. **프레임 로직은 가벼웠다.** `update` 한 번이 평균 1.2ms. 창 크기 조절 때 CPU의 대부분은 우리 코드가
   아니라 **그래픽 드라이버의 화면 전환(SwapBuffers) 대기**(약 10~15ms/회)였다. 아무것도 안 그리는 빈
   eframe 창도 같은 조건에서 49fps에 CPU 포화라서, 이 PC(Intel+NVIDIA 겸용)에서는 창 하나를 한 번 그릴
   때마다 이 비용이 든다.
2. **그린 것과 같은 화면을 또 그리고 바꿔치기(swap)하고 있었다.** eframe은 즉시 모드 하위 창(우리의 메인
   창·스티커·캘린더 전부)을 부모 프레임마다 전부 다시 그리고 swap한다. 어느 한 창에 마우스만 움직여도
   스티커 N개가 N번 swap. 여기에 호스트(보이지 않는 1×1 창)도 매번 swap.
3. **프레임 반복 깨우기.** 100~250ms마다 전체를 깨워 단축키·트레이·알람을 확인했다(유휴 CPU 약 3%).
   스티커가 있으면 그 수만큼 swap이 곱해졌다.
4. **캐럿 깜박임.** 스티커 제목 칸에 입력 커서가 있으면 초당 약 9번 프레임이 돌았다(창마다 swap).

## 고친 것
- **같은 화면은 그리지 않는다** (`vendor/eframe`, eframe 0.31.1의 `glow_integration.rs`만 수정).
  창마다 직전에 그린 화면의 지문(정점·색·텍스처·크기·배율)을 기억해, 같으면 그리기와 swap을 건너뛴다.
  텍스처 변경·사용자 그리기 콜백이 있으면 항상 그리고, 3초가 지나면 같아도 한 번 다시 그린다.
  호스트 창 swap도 이 규칙으로 사라진다. 창 크기 조절 중 프레임 수: 3초에 약 110 → 약 165(+45%, 빈 창
  기준선 3초에 약 150~155).
- **유휴 시 깨우지 않는다.** 단축키는 전용 스레드가 기다렸다가 프레임을 깨우고(`wake.rs`), 트레이
  클릭·두 번째 실행도 같은 방식이다. 고정 틱을 없애고, **다음에 할 일이 있는 시각까지** 잔다: 다가오는
  알람, 자동 잠금 만료, 저장 대기(2초), 트레이 안내, 시간별 정리, 최대 30초. 유휴 CPU 약 3% → 0%
  (스티커 8개 있어도 0%).
- **캐럿은 깜박이지 않는다**(`ui::apply`). 항상 보이는 캐럿. 깜박임 하나가 창 전체 다시 그리기·swap을
  초당 수 회 일으켰다.
- 릴리스 빌드: `opt-level=3`, `lto="fat"`, `codegen-units=1`, `strip` (실행 파일 약 0.7MB 작아짐).
- `vsync`를 끔(`NativeOptions`): 프레임 속도를 화면 주사율에 묶지 않는다. 호스트 창 `visible=false`.

## 같이 발견한 문제 (수정함)
- **`cargo test`가 사용자 실제 `%APPDATA%\OhMemoJang\settings.txt`를 덮어쓰고 있었다.** 테스트가 임시
  폴더를 `data_path`로 저장했고, 그 뒤 앱을 실행하면 그 임시 폴더(빈 데이터)를 읽었다. 테스트에서는
  설정 파일을 읽거나 쓰지 않게 했다(`prefs::Prefs::path`). 이 PC의 `settings.txt`에서 임시 폴더를 가리키던
  `data_path`를 지워 원래 폴더(`%APPDATA%\OhMemoJang\data`)로 되돌렸다. 실제 메모 DB는 건드려지지 않았다.

## 한계 / 확인하지 못한 것
- 창 크기를 끄는 동안 CPU가 높은 것(드라이버 대기)은 그대로다. 빈 창도 같다. 겸용 그래픽(Intel+NVIDIA)
  PC에서는 Windows 설정 → 시스템 → 디스플레이 → 그래픽에서 OhMemoJang을 ‘절전(내장 그래픽)’으로 두면
  줄 수 있다고 보지만 직접 시험하지는 않았다(시스템 설정이라 바꾸지 않았다).
- 스티커 창 하나마다 작업 집합이 약 25MB 늘어난다(창마다 드라이버가 잡는 그래픽 메모리). 창을 닫으면
  줄어드는지는 확인하지 않았다.
- wgpu 렌더러는 시험만 했고(빈 창 373MB) 메모리가 더 커서 쓰지 않았다.
- 같은 화면 건너뛰기는 창을 가렸다 다시 보일 때 내용이 남아 있다는 DWM 동작에 기대고 있다. 그래서 3초가
  지난 뒤의 첫 프레임은 다시 그린다. 이 PC에서는 화면이 깨지는 것을 보지 못했지만 다른 PC에서는 확인하지
  못했다.
- 아직 안 한 것: 페이지별(전체메모 표·위키·캘린더) 그리기 비용, 클립보드 기록 스레드, 이미지 캐시의 장기
  사용량. 다음 단계에서 같은 방식으로 측정한다.
