# 트레이 종료: 순차 정리와 강제 종료

## 요청
트레이 아이콘 우클릭 메뉴의 "종료"가 종료되지 않는 문제를 해결한다. 종료 시 프로그램 종료 강제
명령을 내리고, 작업들을 순차적으로 마무리한 뒤 종료해야 한다.

## 재현 결과 (먼저 확인한 것)
격리한 `APPDATA`(실제 데이터와 분리)로 릴리스 빌드를 띄우고, 트레이 창에 메뉴 명령
(`WM_COMMAND`)을 보내 "종료"를 눌렀다. 보낸 명령은 트레이 메뉴가 실제로 보내는 것과 같다.

- **"종료"가 먹지 않는 현상은 재현하지 못했다.** 일반 시작, `--tray`(메인 창 숨김), 스티커 5개,
  이 PC 실제 프로필 복사본, 창 이동 모달 루프 중, 종료·열기·새 스티커를 연달아 보낸 경우 모두
  기존 코드가 0.01~0.08초에 종료했다. (처음 `--tray`에서 실패한 것은 키보드로 메뉴를 고르려던
  검증 스크립트의 문제였다. 앱 창이 없어 포그라운드 권한이 없었다.)
- 대신 코드에서 다음 결함을 확인했다. 사용자가 보는 증상의 원인일 수 있다.
  1. **트레이 아이콘이 남는다.** 기존에는 `autosave` 직후 `std::process::exit(0)`로 끝냈다. 이
     경로는 `TrayIcon`의 Drop을 건너뛰므로 `NIM_DELETE`가 호출되지 않아, 프로세스가 사라진 뒤에도
     아이콘이 작업 표시줄에 남고 마우스를 올려야 사라진다. 다시 눌러도 반응이 없다.
     (tray-icon 0.26.1의 `Drop`이 `remove_tray_icon`을 부르는 것을 소스로 확인했다. 작업 표시줄에서
     아이콘이 남는 모습을 직접 관찰하지는 못했다. UI Automation으로는 잡히지 않았다.)
  2. **프레임 루프가 막히면 종료 명령이 처리되지 않는다.** 종료 요청은 `update` 안에서만
     읽었다. 프레임 루프가 멈춘 동안에는 메뉴 이벤트가 채널에 쌓이기만 한다.
  3. **정리가 건너뛰어진다.** `exit(0)`는 `on_exit`, App의 Drop(DB 연결 닫기, 전역 단축키 해제),
     GL 컨텍스트·창 정리, 클립보드 스레드 정리를 하지 않는다. 종료 직후 `data.db-wal`, `data.db-shm`이
     남았다.

## 변경

### 새 모듈 `src/quit.rs`
- 종료 단계 상태(`RUNNING → REQUESTED → WRAPPING_UP`)와 **감시자 스레드**.
  `quit::request()`는 어느 스레드에서든 부를 수 있고, 첫 요청에서만 감시자를 건다.
- 감시자는 `TerminateProcess`로 프로세스를 끝낸다.
  - 요청 뒤 **3초** 안에 프레임 루프가 정리를 시작하지 않으면 종료(루프가 막힌 경우).
  - 정리를 시작했어도 **10초**를 넘으면 종료(정리가 멈춘 경우).
- 기한과 종료 동작을 필드로 두어 테스트에서는 짧은 기한과 "종료했다는 기록만" 남기는 인스턴스를 쓴다.

### 트레이 (`src/tray.rs`)
- 메뉴 항목이 선택되는 즉시 호출되는 콜백(`MenuEvent::set_event_handler`)을 등록했다. 종료는
  여기서 바로 `quit::request()`를 부르므로 프레임 루프와 무관하게 접수되고 감시자가 걸린다.
  콜백은 화면 갱신도 요청해서 열기·새 스티커 메모도 다음 틱을 기다리지 않는다.
- 이벤트 채널 경로도 그대로 읽어, 콜백을 못 걸어도 동작한다.

### 순차 정리 (`App::wrap_up`, `src/main.rs`)
종료가 접수된 뒤 첫 프레임에서 아무 창도 그리지 않고 아래 순서로 정리한다. 그리지 않으므로
eframe이 그 프레임에서 모든 하위 창을 닫는다.
1. 트레이 아이콘 제거(Drop → `NIM_DELETE`).
2. 전역 단축키 해제.
3. 스탠딩 캘린더의 바탕화면 클릭 감시(마우스 훅 스레드) 해제.
4. 클립보드 기록의 두 스레드 정지, 저장 스레드가 DB를 닫을 때까지 최대 1.5초 대기
   (`ClipboardHistory::shutdown`, 스레드 수를 세는 `ThreadGuard`).
5. 설정 저장, 바뀐 메모 전부 강제 저장.
6. 루트 뷰포트에 `Close`를 보낸다.

그다음 프레임에서 eframe이 이벤트 루프를 끝내고 `on_exit` → App Drop(DB 연결 닫기) → GL 정리 →
`run_native` 반환 순으로 진행한다. `main`은 종료 요청이 있었다면 그 즉시 `TerminateProcess`로 프로세스를
끝낸다(저장과 창 정리가 끝난 뒤이므로 안전하다).

- eframe은 닫기 요청을 그것을 실은 프레임이 끝난 뒤에 판단한다. 처음 구현에서는 다음 프레임에서
  바로 강제 종료를 걸어 eframe보다 먼저 프로세스를 죽였고(`on_exit`, `Drop` 미호출), 임시 로그로
  이를 찾아 고쳤다. 지금은 그 프레임과 한 프레임을 더 두고, 그래도 루프가 남아 있으면 종료한다.
- 이 변경으로 `ViewportCommand::Close`가 루트에서 동작하지 않는다던 기존 주석(2026-11-12 기록)은
  사실이 아니었다. 루트 프레임이 한 번 더 돌아야 한다.

### 클립보드 기록 (`src/clipboard_history/`)
- `Shared.threads`와 `ThreadGuard`로 저장 스레드와 리스너 스레드의 수명을 센다. 저장 스레드는
  DB(`Store`)를 닫은 뒤에 수가 줄도록 가드를 가장 먼저 선언했다.

## 검증

### 자동 테스트
- `cargo test --release` 241개 통과, 13개 ignored. `cargo clippy --release --all-targets -- -D
  warnings`, `cargo fmt --check` 통과.
- `quit::tests` 4개: 첫 요청만 인정, 요청 전에는 정리 시작 불가, 기한별 판정, **막힌 프레임 루프는
  감시자가 종료**, 정리가 멈춰도 더 긴 기한에 종료.
- `storage::tests::wrap_up_saves_in_order_then_closes_and_ends_a_loop_that_stays`: 저장되지 않은 마지막
  수정이 창이 닫히기 전에 디스크에 있고, 트레이·단축키가 정리되고, `Close`가 한 번만 나가며,
  루프가 남아 있으면 두 프레임 뒤 종료한다.

### 실제 프로세스 (격리 `APPDATA`, 릴리스 빌드)
같은 방식으로 기존 코드와 비교했다. 종료까지 걸린 시간이다.

| 상황 | 기존 | 변경 후 |
|---|---|---|
| 일반 시작 | 0.04초 | 0.09초 |
| `--tray` | 0.08초 | 0.15초 |
| `--tray` + 스티커 5개 | 0.03초 | 0.15초 |
| 이 PC 프로필 복사본 | 0.11초 | 0.11초 |
| 이 PC 프로필 복사본, `--tray` | 0.11초 | 0.13초 |
| 종료·열기·새 스티커 연타 | | 0.17초 |
| 창 이동 모달 루프 중 | 0.11초 | 0.12초 |

- 모든 경우 종료 코드 0, 잔류 프로세스 없음.
- 기존 코드는 정리를 건너뛰는 만큼 조금 더 빠르다. 변경 후에는 프레임 한두 번(약 0.1초)이 더 든다.
- 스티커를 만든 뒤 종료하면 두 코드 모두 메모 13행이 저장되고 DB 무결성 검사를 통과한다.
  변경 후에는 종료 직후 `data.db-wal`, `data.db-shm`이 남지 않는다(기존에는 남았다).
- 임시 로그로 종료 순서(`wrap_up` → `on_exit` → `App` Drop → `run_native` 반환)를 확인한 뒤 로그는 제거했다.

## 확인하지 못한 것
- 사용자가 겪는 정확한 조건. 이 PC에서는 "종료가 안 되는" 상태를 만들지 못했다. 위 결함이 원인이라는
  것은 코드 근거이며, 남은 아이콘을 실제로 눈으로 확인하지는 못했다.
- 프레임 루프가 실제로 막힌 프로세스에서 감시자가 동작하는지. 막힌 루프(대화상자 등)를 안정적으로
  만들 방법이 없어 감시자는 단위 테스트로만 확인했다. 창 이동 모달 루프에서는 루프가 계속 돌아
  감시자가 필요하지 않았다.
- 스탠딩 캘린더가 바탕화면에 고정된 상태에서의 종료. 해제 코드는 단순하지만 직접 돌려 보지 않았다.
- Windows 로그오프·시스템 종료 중의 정리(이번 범위 밖).

종료 후에도 같은 증상이 있으면, 종료 시점의 상태(메인 창 열림 여부, 스티커 수, 스탠딩 캘린더,
열려 있던 대화상자)를 알려주면 그 조건으로 재현한다.
